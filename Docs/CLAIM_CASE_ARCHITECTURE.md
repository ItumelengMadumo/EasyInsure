# Claim Case and Communication Architecture

## Case identity

Every newly submitted claim has two separate references:

- `policeCaseNumber` is supplied by the client and supported by a mandatory affidavit.
- `claimNumber` is generated by EasyInsure only when the draft is successfully submitted.

Legacy claim rows remain readable while the command layer enforces the new requirements for every new submission.

## Durable case record

The claim is the case aggregate. Its permanent history is stored in append-oriented records:

- `ClaimAssignment` retains every lead and supporting team assignment with identity snapshots.
- `ClaimActivity` contains client-safe progress and event summaries.
- `ClaimCommunication` contains the chronological client-facing conversation across channels.
- `ClaimInternalNote` is a separate staff-only record and cannot be queried by clients.
- `CommunicationDelivery` retains external delivery attempts and failures.
- `CallRecord` captures call metadata, outcome, consent, notes, and future transcript/recording keys.
- `InboundReconciliation` holds external messages that cannot be matched safely.

Identity snapshots deliberately preserve the name and role displayed at the time of an event.

## Submission and lifecycle

The client creates a resumable draft, uploads the affidavit into quarantine, and then finalises it. Finalisation is idempotent, generates the EasyInsure claim number, and attempts least-loaded lead-advisor assignment. If no active advisor profile is available, the case remains in `ASSIGNMENT_PENDING` with a fifteen-minute assignment SLA.

The supported lifecycle is:

```text
DRAFT
  → ASSIGNMENT_PENDING
  → VALIDATING
  → UNDER_ASSESSMENT
  ↔ INFO_NEEDED
  → DECISION_PENDING
  → APPROVED → PAYMENT_PENDING → PAID → CLOSED
  → REJECTED → CLOSED
```

All final financial decisions remain senior-only.

## Authorization

- Clients use owner authorization and only receive client-safe activity and communication models.
- Junior and intermediate officers cannot list all Claim records. They receive an assigned-case portfolio from a server resolver that verifies active `ClaimAssignment` records.
- Senior officers and superusers can inspect the complete portfolio.
- Internal notes, delivery diagnostics, call details, claim analysis, and audit records are not client-readable.

## Communication adapters

Portal communication is active immediately. Email, SMS, and WhatsApp messages enter an encrypted SQS queue and pass through channel adapters. The initial adapters intentionally return `DISABLED` until a provider is configured.

The signed inbound webhook normalizes external messages and delivery callbacks. It deduplicates provider references, associates messages using the EasyInsure claim number, and sends unmatched messages to reconciliation.

Before enabling a provider:

1. Store an HMAC webhook secret and expose it to `communication-webhook` as `COMMUNICATION_WEBHOOK_SECRET`.
2. Replace the disabled adapter with the provider SDK call.
3. Configure provider signature/header mapping to the normalized webhook contract.
4. Confirm POPIA, consent, recording, transcript, and document retention policies.

## Account closure

The profile page creates an account-closure request, anonymises direct profile identifiers, and deletes the current Cognito user. Claims, financial decisions, audit events, and communications remain archived under the versioned retention policy. Production retention durations require compliance approval.
